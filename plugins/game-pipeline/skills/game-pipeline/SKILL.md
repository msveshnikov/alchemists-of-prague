# Game pipeline: concept art → Blender → Godot → shipped build

This is the workflow used to build *Alchemists of Prague* (a Gothic 1–2 style action RPG in medieval
Prague): a whole game where **no asset is made by hand**. Concept art comes from ChatGPT, everything 3D
is generated by Python scripts running in Blender, and Godot assembles the game at runtime from JSON
that Blender writes. Any file can be rebuilt with one command.

## Tools the user needs

- **Claude Code desktop app** (for the built-in browser) and a **ChatGPT account** signed in there.
  No image API keys: art is ordered through the ChatGPT web UI like a person would.
- **Blender 5.x** (4.2+ works) — run headless: `blender -b --factory-startup -P script.py -- args`.
  Blender MCP / Godot MCP are optional; the pipeline never waits for them.
- **Godot 4.x** (project made on 4.7.2) with export templates for Windows, Web, Android
  (Android also needs the SDK/JDK and a debug keystore).
- **Python 3** with `numpy pillow opencv-python` for image tooling outside Blender.
- Optional: a web server reachable over `scp` for hosting the Web build and APK.

Find the Blender and Godot executables first (often not on PATH) and write their paths into the
project's README and memory, so later sessions don't search again.

## The pipeline at a glance

1. **Design doc** (`<Game> — concept art and tasks.md`): pitch, hero, enemies, mechanics, a **style
   block** pasted at the start of every art prompt, day/night add-ons, and prompts for every location
   (day, night, *empty* version), every character (character sheet), every UI screen, plus a top-down
   world map. → 01
2. **Concept art** via ChatGPT in the built-in browser: generate the best image first, then feed it
   back as a reference ("keep exactly the same art style as the reference image") for all the others.
   Save into `concept/locations|characters|empty|ui/` with meaningful names. → 05
3. **Five task files**, each self-contained and run in order by an autonomous Claude Code session:
   - `task1.md` environment & props in Blender
   - `task2.md` characters: models, rigs, animations
   - `task3.md` empty level(s): layout, markers, day/night lighting
   - `task4.md` population: NPCs, enemies, effects, schedule
   - `task5.md` the game in Godot: controls, combat, UI, economy, save/load, sound, builds → 02
4. **Vertical slice first**: run task1–5 for ONE location (the most detailed one). Play it, fix the
   task files, and only then run task1–5 again for the remaining locations ("run 2"), and finally
   stitch everything into one open world.
5. **Every task leaves a paper trail**: `decisions.md` (every choice made without asking),
   `issues.md` (what failed and the workaround), `report_taskN.md` (what was done / not done),
   `props_list.md`, `characters_list.md`, preview renders, README "Rebuild" section.
6. **Iterate with reference art** whenever something looks primitive (e.g. the in-game map): ask
   ChatGPT for a better prompt first, then the image, then make it fit the game exactly (align it to
   a render of the real layout). → 05
7. **Finish every task by shipping**: commit everything, export Windows + Web + Android, upload,
   open the live page and check it. Don't ask — this is the standing rule. → 06

## Principles that made it work

- **Autonomous mode** in every task file: no questions, decide and log in `decisions.md`, try another
  approach on failure, log to `issues.md`, never stop before the end, write a report.
- **Everything procedural**: models, numpy-painted textures, rigs, skin weights, animations, level
  layout, population, UI textures, icons — all Python. No manual Blender clicks, so every fix is a code
  change and a re-run.
- **Blender writes data, Godot reads it**: glTF assets + `*_layout.json` / `*_population.json`. The
  Godot scene is assembled at runtime from JSON, so a rebuilt level shows up in the game with no
  manual scene editing.
- **Strict conventions** shared by all tasks (units, facing direction, node-name prefixes like
  `INT_door_*`, `MARK_*`, `LIGHT_*`, `*-colonly`). Put them in `decisions.md` in task1 and obey them
  afterwards. → 03
- **Look at the result**: render previews and contact sheets in Blender, take in-game screenshots
  with a scripted tour, compare against the concept art, fix, repeat. Never call something done
  without seeing it.
- **Only free/open assets** if anything is downloaded (CC0/CC-BY: Freesound, OpenGameArt, Kenney,
  Quaternius, Godot Asset Library), each listed in `assets/CREDITS.md`. No paid 3D generators.
- **Self-test**: an `--autotest` mode plays the game (move, fight, trade, enter house, throw an enemy
  out of a window, night, save/load, death) and writes screenshots + a log; a `--tour` mode shoots
  given spots. Run them after every change.

## Starting a brand-new game

1. Ask the user for the pitch only if there is none; otherwise draft the design doc yourself from
   01's template (setting, art style reference, hero, enemies, core mechanics, locations, UI screens).
2. Create the folder layout: `concept/{locations,characters,empty,ui}`, `blender/scripts`,
   `assets/{architecture,props,characters,textures,levels,ui,audio}`, `scripts/`, `renders/`, `build/`.
   Put a `.gdignore` in `concept/` and `concept_art/` so Godot doesn't import reference images.
3. Order the concept art (05). Ask before each download, as the browser rules require.
4. Write `task1.md`–`task5.md` from 02, scoped to the vertical-slice location.
5. Run them one at a time (a fresh session per task works best; each reads the previous reports).
6. Ship (06). Then expand to the other locations with run 2 of the tasks.

## Adding to an existing game made this way

- New location: write run-2 style task1–5 sections for it (02), reuse the libraries in
  `blender/scripts/lib_*.py`, add a `build_<location>` step, then stitch it into the world builder.
- New look for something: order reference art (05), then change the generator code, re-run, compare.
- Always finish with 06.
